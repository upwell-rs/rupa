# Milestone 3: derives and capabilities

Status: **implemented.** We agreed on 2026-10-03 that the main way to work is
one model (the entity itself), with typed insert and patch structs available
as an opt-in.

## Capability traits (`rupa_core::capability`)

Each trait is generic over the target entity `E` and is implemented by the
value that takes part in the operation:

| trait | implemented by | used by |
|---|---|---|
| `Gettable<E>` | `E` | `get::<E>(&id) -> Query<Option<E>>` |
| `Insertable<E>` | `E` (one model) or `NewE` (`#[insertable(entity = E)]`) | `insert::<E>().value(&v)` → `.affected()` / `.returning_one()` / `.returning_all()` |
| `Updatable<E>` | `E` (full update by id) or a patch (`#[updatable(entity = E)]`) | `update::<E>().one(&v)` (keyed) / `.apply(&v).filter(..)` |
| `Deletable<E>` | `E` | `delete::<E>().one(&e)` / `.by_id(&id)` / `.filter(..)` |

### Gating

The write builders require these traits, so an entity that only derives
`Entity` cannot be written to at all:

- `insert().value` requires `V: Insertable<E>`.
- `update().set` and `set_expr` require `E: Updatable<E>`.
- `delete::<E>()` requires `E: Deletable<E>`.

Reading with `select::<E>()` stays ungated. Each refusal comes with a message
saying which derive to add.

### Keyed and unkeyed updates

`Updatable::Key` is either `Keyed<E::Id>` or `NoKey`. `.one()` requires
`Key: RowKey`. If you pass it an unkeyed patch, the compiler says "this update
value does not identify a row", and points you to `#[id]` or to
`.apply().filter()`.

## Derives (`rupa-macros`, re-exported by `rupa`)

### `#[derive(Entity)]`

Emits `Entity` and `FromRow`, and nothing else.

| attribute | meaning |
|---|---|
| `#[entity(table = "..", schema = "..")]` | Required; the table name is never inferred. |
| `#[id]` / `#[id(generated)]` | Exactly one id field. Composite ids are rejected with a "not supported yet" error. |
| `#[column(name = "..")]` | Column name; defaults to the field name. |
| `#[column(scalar \| json)]` | Overrides the inferred column kind. |
| `#[column(generated)]` | The database supplies the value. The column is skipped by entity-level insert and update, and is not required in `NewE` structs. |

- **Generic entities are rejected.** Kind inference only works on concrete
  types.
- **Hidden items:** the derive also generates `__rupa_fields()` (one probe per
  field), `__RUPA_INSERT_REQUIRED` and `__RUPA_ID_FIELD`. `col!` and the
  companion derives go through these, so a column's name and kind are decided
  in exactly one place.
- **Column-kind overrides are honoured everywhere.** Fields with
  `#[column(scalar)]` or `#[column(json)]` get a dedicated probe type whose
  inherent method wins over the inference traits. Previously, `col!` would
  silently have re-inferred them.

### Capability derives

Each emits exactly one impl. On companion structs they also emit compile-time
checks:

- **Every field must exist on the entity with the same type.** A mismatch
  reports this, at the field: *"this field's type `Option<String>` does not
  match the entity's field"*.
- **`NewE` must provide every non-nullable, non-generated entity field.** This
  is a const assertion. It names the missing field and suggests adding it or
  marking it `#[column(generated)]`.
- **Patch fields must be `Option<_>`.** Nullable columns use
  `Option<Option<_>>`.
- **A patch's `#[id]` field must be the entity's id field.**

### Crate path

Generated code refers to `::rupa::__macro_support`. Crates that depend on
`rupa-core` directly can set `#[rupa(crate = rupa_core)]`.

## IR and backends

- **`Insert.returning: Option<Vec<ColumnRef>>`.** The renderer emits
  `RETURNING`. Dialects without the `Returning` capability get
  `RenderError::UnsupportedCapability`; Postgres has it.
- **`ColumnMeta.generated`** marks database-supplied columns.
- **Memory backend:**
  - Supports `RETURNING`. The `Memory` dialect now declares `Returning`.
  - Fills omitted generated integer columns with a per-table identity
    sequence, matching `GENERATED BY DEFAULT AS IDENTITY`.
  - A generated column of any other type that is left out is `Unsupported`.
  - It differs from Postgres when an insert fails: the sequence is restored,
    whereas Postgres consumes those values.

## Tests

- **Conformance:** the suite now uses derived entities and has 21 cases. A new
  `Note` entity covers:
  - identity ids through `RETURNING`;
  - one-model insert;
  - `get`;
  - full, keyed-patch and unkeyed-patch updates;
  - keyed deletes.

  All pass on memory (sync and async) and both Postgres drivers.
- **`rupa-macros/tests/derive.rs`:** end-to-end derive tests, plus 13
  compile-error cases. They cover:
  - a missing table, a missing id, composite ids and generic entities;
  - unknown options and unstorable field types;
  - no write surface on an entity without capabilities;
  - companion field errors: unknown field, wrong type, missing required field;
  - patch errors: field not `Option`, wrong `#[id]` field, unkeyed patch
    passed to `.one()`.
- **Hand-written fixture:** the `rupa-core` fixture implements its
  capabilities by hand, which keeps the no-derive path tested.

## Known rough edges
- ~~`MemoryDb` implements both executor traits~~ Resolved: `MemoryDb` is sync only, and
  `AsyncMemoryDb` (`db.into_async()`) is the async executor, so each type implements one
  executor trait.
- **No `Gettable` projections** (`#[gettable(entity = ..)]`) yet. The trait is
  already generic, so adding them won't break anything.
- **`Deletable` exists only on the entity.** There are no key structs.
- **A wrong-typed companion field reports its error twice.** Both copies say
  the same thing.
