# Joins

> **Updated by #39:** `col!(Entity::field)` is now the derived constant `Entity::FIELD`, and `E::columns()` the constant `E::COLUMNS`. The design below keeps the original spelling.

Status: **built** (2026-10-18), on branch `joins`. All seven steps of the
build order are done:

1. the IR, rendering (aliases `t0`, `t1`, ..), render-cache shapes, and
   nested-loop joins in the memory backend;
2. `Src` handles, the join builder for up to 10 sources, and tuple decoding;
3. `on!`;
4. declared relations and inferred joins (`join::<J>().inner()`);
5. `#[derive(Joined)]` merged entities;
6. joins in `#[query]` (and so in repositories);
7. self-joins: aliases in `#[query]`, pinned sources in `Joined`.

They are covered by join conformance cases on every backend.

The spec listed joins as a non-goal, but asked to keep the IR "join-ready".
That non-goal is now lifted. Lazy loading, the identity map and automatic
relation loading **stay** non-goals: a join returns flat rows, and nothing
is fetched behind the user's back.

## What the code already allows

From milestone 1:

- `ColumnRef` carries a `SourceId`, which is always `SourceId(0)` today.
- `FromClause` is an exhaustive enum with a single `Table` variant. Adding a
  variant breaks every renderer's match and the memory backend's
  `let FromClause::Table(t) = ..`, which is the intent.
- Projection is positional (`Vec<ColumnRef>`), and rows are decoded by
  position.
- Known gap 4 in milestone-1: `Expr<T>` doesn't check which entity a column
  belongs to, so `select::<User>().filter(Other::COL.eq(..))` compiles. That
  note says to fix it when joins arrive, so this design includes the fix.

## Scope of v1

In scope:

- `INNER JOIN` and `LEFT JOIN`, with an explicit `ON` condition. These behave
  the same on Postgres, MySQL and SQLite, so they need no capability.
- Up to 10 sources (the base table plus 9 joins), including the same table
  twice (self-joins).
- Filtering and ordering on any source's columns. `exists()` on a join.
- Results as tuples: `(User, Order)`, and `(User, Option<Order>)` for a left
  join.
- **Merged entities.** Instead of a tuple, the rows can decode into one new
  struct whose fields come from several entities (`#[derive(Joined)]`, see
  below).
- **Declared relations** (`#[column(references = User)]`). With these, a join
  can leave out its `ON` condition.
- The builder API first, then `#[query]` support.
- The memory backend (nested-loop join) and the conformance suite.

Out of scope for v1:

- `RIGHT JOIN` / `FULL JOIN`. MySQL has no `FULL`, and SQLite only has both
  from 3.39. If they're added later, gate them behind a capability.
- `UPDATE`/`DELETE` with joins (the syntax differs per dialect).
- Grouping one-to-many results into nested `Vec`s. That is relation loading;
  users group the flat rows themselves.
- Aggregates, `GROUP BY` and subqueries.

## No inference from names

Following hard rule 1, nothing guesses that `Order.user_id` refers to
`User.id`. An `ON` condition is either written out, or it comes from a
relation the author declared with an attribute (see "Declared relations").

## IR changes (rupa-core)

```rust
pub enum FromClause {
    Table(TableRef),
    /// The first source is SourceId(0); each join adds the next id, in order.
    Join { base: TableRef, joins: Vec<Join> },
}

pub struct Join {
    pub kind: JoinKind,            // Inner | Left  (exhaustive)
    pub table: TableRef,
    pub on: ExprNode,
}
```

- **Source numbering.** Sources are numbered by position: the base table is
  `SourceId(0)`, and the n-th join is `SourceId(n)`. The IR stores no alias
  strings.
- **Rendering.** The renderer aliases each source as `t0`, `t1` and so on.
  The alias is derived from the `SourceId`, so it is still static text. Single
  table statements stay unqualified, so their SQL and cache keys don't change.
- **Projection.** `ColumnRef`s from several sources, concatenated in source
  order.
- **Filters on updates and deletes.** `Update`/`Delete` keep a single
  `TableRef`. Any `ColumnRef` in their filter must be `SourceId(0)`. The
  renderer checks this and returns an error otherwise.

## Typed builder

Expressions on a join have to name their source. The proposal is a source
handle `Src<E, const N: u16>`. Its methods take only `Column<E, ..>`, which
closes known gap 4 for joined queries:

```rust
let rows: Vec<(User, Option<Order>)> = select::<User>()
    .left_join_on::<Order>(|(u, o)| o.col(col!(Order::user_id)).eq(u.col(col!(User::id))))
    .filter(|(u, _)| u.col(col!(User::active)).eq(true))
    .order_by(|(_, o)| o.col(col!(Order::placed_at)).desc())
    .all()
    .run(&mut db)?;
```

- **Join builder type.** `left_join_on`/`inner_join_on` turn `SelectBuilder<User>`
  into `JoinBuilder<(Src<User, 0>, Src<Order, 1>), (User, Option<Order>)>`.
  The second parameter is the row type. Each further join adds a source and a
  tuple element.
- **Up to 10 sources.** The impls for each arity are generated by
  `macro_rules!`, so the only cost is more generated code. It doesn't touch
  the IR or the renderers, which take any number of sources.
- **Closures.** The `on`/`filter`/`order_by` closures receive the source
  handles. A self-join gets two different handles of the same entity
  (`Src<User, 0>`, `Src<User, 1>`), so `manager.col(..)` and
  `employee.col(..)` can't be mixed up.
- **Single-table builder unchanged.** `Column::column_ref()` keeps producing
  `SourceId(0)`, so existing code doesn't change. Fixing gap 4 there too
  would mean giving `Expr` an entity parameter, which breaks the DSL and
  `#[dsl::function]` signatures. That stays a separate decision.

As built (step 2):

- **Sources live on the column.** `Column` carries a `SourceId`, which is 0
  by default. `Src::col` returns the same handle re-pointed at its source, so
  every existing operator (`eq`, `like`, JSON paths, `asc`, ..) works on
  joined columns unchanged.
- **Plain columns mean the first source.** A column used in a join closure
  without going through a handle refers to the first source. That is
  intended for filters added before the join, and it is still valid after
  one. It is also a known footgun: `col!(Order::total)` written without
  `o.col(..)` is source 0, and the database then rejects `t0.total`. So the
  mistake fails loudly, but only at run time.
- **Closures return `Expr<bool>`,** not `impl IntoExpr<bool>`. With a generic
  return type the turbofish would have to be `::<Order, _>`. With `Expr<bool>`
  it is just `::<Order>`.
- **Closures take one tuple of handles,** `|(u, o)|`, not one argument per
  source, which is what `on!` needs (step 3). A macro can't write a closure
  whose arity it doesn't know, but it can write `|sources| ..` over a tuple.
  It also made `filter`, `order_by`, `limit` and the result methods a single
  generic impl. Only the next-join methods are per arity.
- **Names (decided 2026-10-18).** The closure forms are `inner_join_on` and
  `left_join_on`. Joins inferred from declared relations are
  `.join::<J>().inner()` / `.left()` (step 4: Rust has no partial turbofish,
  so they can't be `inner_join::<J>()`).

### `on!` for the common case

For simple conditions there is a shorter form. It expands to the closure
above:

```rust
select::<User>()
    .left_join_on::<Order>(on!(Order::user_id == User::id))
    .filter(on!(Order::total > $min && User::prefs.theme == "dark"))
```

- **How it works.** `on!` uses the same grammar as `#[query]` (`==`, `!=`,
  `<`, `&&`, `||`, `!`, `in`, `like`, `is_null`, JSON paths and DSL calls),
  with fields written `Entity::field`. It expands to
  `|sources| -> Expr<bool> { .. }`. Each field becomes
  `source_col(&sources, column)`, and `Has<E, At<N>>` (one impl per tuple
  position) infers where `E` sits in the tuple.
- **`$name` binds a variable in scope** by cloning it, so the variable can
  still be used afterwards. In `#[query]`, `$name` must be a parameter of the
  function; in `on!`, it can be any variable.
- **Errors.**
  - An entity that isn't a source: "`Item` is not a source of this join".
  - An unqualified field: "name the field's entity: `Entity::user_id`".
  - `Entity::field` inside `#[query]`: rejected until step 6.
  - An entity that is a source twice (a self-join): Rust's own
    "type annotations needed" (E0283). The error lists the two candidate
    positions, but stable Rust can't customize ambiguity errors, so the
    message doesn't mention the handles. Use the closure form there.

## Declared relations

```rust
#[derive(Entity)]
struct Order {
    #[id] id: i64,
    #[column(references = User)] user_id: i64,
    #[column(references = User, relation = reviewer)] reviewed_by: Option<i64>,
}
```

- **What the attribute means.** `references = User` says this column holds
  `User`'s id, so `User::ID_COLUMNS` must have exactly one column. The derive
  checks that the column's type matches `User::Id`, allowing for `Option`.
- **What the derive generates.** For each `references` field, the derive
  generates a hidden marker type `R` for the relation and two impls:
  - `impl JoinTo<User, Fwd, R> for Order`, for `Order` joined onto a `User`
    source;
  - `impl JoinTo<Order, Rev, R> for User`, for the reverse. Order's crate may
    write this impl, because `Order` is local and appears in the trait's
    parameters.

  Both build the `ON` condition `order.user_id = user.id`.
- **Inferred joins (decided 2026-10-18: `join::<J>()`, then `.inner()` /
  `.left()`).** Rust has no partial turbofish, so `.inner_join::<Order>()`
  can't also infer the relation's marker types. Picking the entity and
  finishing the join are therefore two calls:

  ```rust
  select::<User>()
      .join::<Order>().inner()    // Order.user_id -> User
      .join::<Line>().left()      // Line.order_id -> Order, at source 1
  ```

  `JoinOnto<J, At<P>, D, R>` is implemented for each tuple position `P`,
  with the bound `J: JoinTo<E_P, D, R>`. The compiler drops the positions
  whose entity has no relation with `J`. So the join compiles when exactly
  one relation fits, at any earlier source and in either direction.
  Explicit conditions use `inner_join_on` / `left_join_on`.
- **Several relations.** When more than one relation fits, as with `user_id`
  and `reviewed_by` above, the join names the one it wants:
  `.join::<Order>().inner_via(Order::reviewer())`. Each relation gets a
  generated accessor returning `Rel<R>`, named by `relation = ..`. If that
  is left out, the name is the field name with a trailing `_id` removed.
  This only names the accessor; the relation itself is declared by the
  attribute.
- **Errors.**
  - No relation: "`Order` has no declared relation to `User`".
  - Several relations: Rust's E0283, which points at the `references`
    attributes that fit.
  - A field whose type isn't the target's id (or an `Option` of it):
    "a `references` field must hold the referenced entity's id".
  - `relation` without `references`: rejected by the derive.
- **Self-references.** A self-reference such as `manager_id` referencing
  `User` fits both ways round: an employee joined to their manager, or a
  manager joined to their reports. So even `via` is ambiguous between `Fwd`
  and `Rev`. Write the condition with `left_join_on` there.
- **Not a foreign-key check.** Relations don't validate anything in the
  database. They only build `ON` conditions. Database foreign keys belong to
  migrations, which come later.

## Decoding tuples

- **Offset row view.** A new `OffsetRow<'a> { row: &'a dyn Row, base: usize }`
  implements `Row` by shifting indexes. A derived `from_row` reads columns
  `0..n`, so it works unchanged when given an `OffsetRow`. Each tuple element
  decodes from `OffsetRow { base: sum of earlier widths }`, where the widths
  come from `E::columns().len()`.
- **Why tuples need their own trait.** We can't simply implement `FromRow` for
  `Option<E>`: the blanket `impl<T: FromRow> QueryResult for T` would then
  overlap with `impl QueryResult for Option<T>`. Instead, tuple elements
  implement a new `JoinPart` trait:
  - `E: Entity` decodes directly.
  - `Option<E>` returns `None` when all of `E`'s id columns are `NULL`. That
    is what a left join produces when nothing matches, because an id column is
    never `NULL` in a real row.
  - `(A, B, ..)` where every element is a `JoinPart` implements `FromRow`. So
    `Vec<(User, Order)>`, `Option<(..)>` and `(..)` all work with the existing
    result shapes.
- **Static check on left joins.** A left join's entity must be decoded as
  `Option<E>`. The builder fixes the row type, so the user can't write
  `(User, Order)` for a left join.

## Merged entities: `#[derive(Joined)]`

A user who doesn't want a tuple declares one struct that combines columns from
several entities:

```rust
#[derive(Joined)]
struct OrderLine {
    #[from(Order::id)]       order_id: i64,
    #[from(User::name)]      customer: String,
    #[from(Order::total)]    total: i64,
    #[from(Coupon::code)]    coupon: Option<String>,   // left-joined
    #[flatten]               user: User,               // a whole entity
}

let lines: Vec<OrderLine> = select::<Order>()
    .join::<User>().inner()
    .join::<Coupon>().left()
    .filter(on!(Order::total > 100))
    .into::<OrderLine>()
    .all()
    .run(&mut db)?;
```

- **Read-only.** A `Joined` struct belongs to the repository side. It isn't an
  `Entity`: it has no table and no id, and no capabilities such as
  `Insertable` or `Updatable`. It is only something rows decode into.
- **It selects only what it needs.** The projection becomes exactly its
  fields, so a join doesn't fetch columns nobody reads.
- **Every field says where it comes from.** It uses `#[from(Entity::field)]`,
  or `#[flatten]` for a whole entity, which is decoded with `JoinPart` as an
  `Option` when left-joined. There is no matching by field name (hard rule 1).
- **Checked against the query.** The derive generates
  `impl<R, ..> Joined<R, M> for OrderLine`. Its bounds require each field's
  entity to be a part of the join's row type `R`
  (`R: PartOf<Coupon, At<P>, Left>`), and a left-joined part admits only
  `Option` fields (`Left: Admits<Opt>`). The row type already records the
  join kind: a left-joined entity appears as `Option<Coupon>`. So
  `coupon: String` above fails to compile with "a field from a left-joined
  entity must be an `Option`".
- **As built (step 5).**
  - `.into::<V>()` takes only `V`. The markers `M` are inferred on
    `.all()` / `.optional()` / `.one()` / `.build::<Res, _>()`, which avoids
    the partial-turbofish problem of step 4.
  - Decoding is the derive's own `FromRow` impl, reading fields in order by
    position. A `#[from]` field reads through `ReadAs<F>`: the column's type
    `T`, or `Option<T>` (`NULL` is `None`). A `#[flatten]` field decodes as
    a `JoinPart` (`E`, or `Option<E>`).
  - Whether a field is "an `Option`" is decided from the field type as
    written. A type alias for `Option` counts as plain, which is the
    conservative choice.
- **Self-joins (step 7).** With the same entity twice, finding a field's
  source by type is ambiguous (E0283). So such fields name their source
  position: `#[from(User::name, source = 1)]`, `#[flatten(source = 1)]`. The
  struct is generic over the join, so it can't use a query's aliases;
  positions are what it has.
- **In repositories.** `#[query]` can return `Vec<OrderLine>` the same way it
  returns tuples.

## `#[query]` (phase 2)

```rust
#[query(
    left_join = Order on Order::user_id == User::id,
    filter = User::active == true,
    order_by = Order::placed_at desc,
)]
fn with_orders(&self) -> Result<Vec<(User, Option<Order>)>, Error>;
```

- **How it is checked.** The return type declares the tuple, and the
  attribute declares the joins. They must agree: the same order, and
  `Option` exactly where a join is a left join. The generated code is the
  join builder ending in `.build::<R>()`, so the compiler checks this:
  "expected `(User, Option<Order>)`, found `(User, Order)`".
- **Three ways to give `ON`.** Each `inner_join` / `left_join` (repeatable,
  in order) takes one of:
  - `on <expr>`, a condition in the filter grammar;
  - `via Entity::relation`, a declared relation picked by its accessor;
  - nothing, in which case the one declared relation decides it
    (`inner_join = Order`).
- **The first source.** It is the tuple's first element. With a `Joined`
  struct result (or `bool`), name it with `entity = Type`.
- **Merged entities.** The return type may be a `Joined` struct instead of a
  tuple; the generated code is `.into::<V>().build::<R, _>()`.
- **Fields need a prefix on joins.** Without joins, a field resolves against
  the single entity, as `field`. With joins, every field, including
  `order_by` keys, is written `Entity::field`. Plain fields are an error
  there, and so is `Entity::field` without joins.
- **Repositories** get the same codegen, so a repository method can join.
  DSL calls in `on` conditions count toward the method's `DslAvailable`
  bounds.
- **Not combinable:** joins with `sql`, or with `get` / `insert` / `update` /
  `delete`.
- **Self-joins (step 7): aliases.** For example:
  `entity = User as employee, left_join = User as manager on manager::id == employee::manager_id`.
  - The macro knows the whole source list, so a qualified field resolves to
    a tuple position (`sources.1.col(..)`). `alias::field` names an aliased
    source, and `Entity::field` names the one source of that entity without
    an alias.
  - An entity that is several unaliased sources is an error asking for
    aliases. An entity that is only joined under aliases is an error listing
    them.
  - Aliases must be unique, and must not be an entity's name.
  - An entity spelled differently from its join (`crate::User` against
    `User`) falls back to the lookup by type.
  - `on!` has no aliases, because it doesn't know the sources. A self-join
    built with the builder uses the closure handles.

## Memory backend

- **Nested-loop join**, building combined rows as the sources' value rows
  concatenated together.
- **Evaluation.** `RowScope` resolves a `ColumnRef` by `(source, name)`.
  Left-join misses are padded with each column's typed `Null`.
- **Ordering** follows Postgres, as for every other backend: a left join
  keeps the base row's order, and then `ORDER BY` applies.

## Conformance

Capability-free cases in `rupa-conformance` (`joins.rs`), run on every
backend (memory, Postgres, MySQL, SQLite, each through every driver):

- inner, left, self-join, and three-way join;
- filter on a joined column;
- order by a joined column with `NULL`s from left-join misses, and limit and
  offset;
- single-row shapes and `exists()` on a join;
- left join decoding to `None`, including an entity with non-null JSON and
  timestamp columns;
- `on!` with JSON paths, a DSL call and `$variables`;
- declared relations in both directions, through `via`, and onto a non-first
  source;
- `#[derive(Joined)]` structs;
- `#[query]` joins, and self-joins through aliases and pinned sources.

Native RLS is Postgres-only (`Capability::NativeRls`), so joins under RLS are
tested in `rupa-driver-tokio-postgres/tests/rls.rs` instead. That test checks
that each table's policy filters its own rows in a join: a comment by
another tenant on a visible doc stays hidden, and a visible comment on a
hidden doc comes back with `None` for the doc.

Malformed IR is an error, not a panic: a column of a source the statement
doesn't have, or of a source joined after the condition that uses it, is
`RenderError::UnknownSource` / `MemoryError::NoSuchSource`.

## Decisions (2026-10-18)

1. **API shape:** both closures and `on!`.
2. **Up to 10 sources.** The cost is generated code only.
3. **Declared relations are part of this milestone,** so that joins can infer
   their `ON` from the types.
4. **No DTOs.** Those belong to the transport layer, not the repository. What
   is supported instead are merged entities, `#[derive(Joined)]`.

## Build order

1. The IR (`FromClause::Join`), the renderer, and the memory backend.
2. `Src` handles, the join builder, tuple decoding (`JoinPart`, `OffsetRow`),
   and conformance cases.
3. `on!`.
4. `#[column(references)]` and inferred joins.
5. `#[derive(Joined)]`.
6. `#[query]` joins.
7. Self-join aliases in `#[query]` and `Joined`.
