# rupa-migrate

## Role

Standalone migration catalog and execution contracts. SQL and compiled Rust
migrations share one immutable history, without requiring async, dynamic
dispatch, a pool, or Upwell.

## Usage

Enable `rupa/migrations` and a supported driver: synchronous SQLite
(`sqlite` or `sqlite-unbundled`), PostgreSQL (`postgres-sync`) or MySQL
(`mysql`), or asynchronous PostgreSQL (`postgres`) or sqlx (`sqlx-postgres`,
`sqlx-mysql`, `sqlx-sqlite`):

```rust,ignore
let entries = application_migrations();
let catalog = Catalog::new("primary", VersionScheme::Numbered, &entries)?;
let report = catalog.apply(SqliteExecutor::open("app.db")?)?; // sync::Apply
```

The catalog takes a dedicated native connection and closes it after the run.
Callers do not construct runner/session wrappers. A connection already in an
application transaction is rejected. Migration bodies receive `Context` for
scripts and typed queries; it exposes no connection, transaction or lock control.

`sql_migration!` embeds a `.sql` file in a zero-sized planned type;
`migration_catalog!` generates a closed enum and typed error enum for a mixed
catalog. A `PlannedMigration` returns a `Plan` of SQL scripts and portable
schema operations (`schema`, re-exported from `rupa-core`), which
`Planned<T>` executes; its checksum covers the plan. Scripted Rust bodies
implement `Migration<S>` and declare their source/helper closure in `Metadata`;
they can run schema operations through `Context::schema`.
`include_migrations!` includes a catalog generated by `rupa-build` from a
migration directory. See `examples/migrations` and `docs/migrations.md`.

## Internal role

Owns version validation, canonical SHA-256 artifact digests (including the
canonical encoding of schema operations), plan inspection, strict ordering, the
apply engine, typed errors and driver session contracts. One internal
`macro_rules!` emits the runner, `Context` methods and `Planned<T>` adapter for
each enabled mode, so sync and async share every step. Sessions bind to
`rupa_core::{sync, asynchronous}::Connection`. Schema operations are
rendered with `rupa-sql` for the session's dialect, and every plan is rendered
before the target is acquired.
Drivers implement `Session` on their native executor and keep lock/history
machinery private. The runner holds a drop guard that calls `Session::abandon`
when a run ends without returning (a dropped future or a panic), so a retained
session refuses further use. Shared driver support also lives here: per-dialect script
grammars for SQLite, PostgreSQL and MySQL (`validate_script` and `split_script`,
refusing runner-owned statements on engines without
a native authorizer), the canonical target identity (`Target`) that derives
lock keys independently of driver and URL, and the typed `StateError` drivers
report for misused migration connections. No boxed body errors or erased catalog dispatch is required.

The runner applies incrementals under the policies a session declares in
`Session::POLICIES`. Changed/missing applied artifacts, duplicate versions and
late arrivals fail with typed `Error::Blocked` blockers, and policies the
session cannot honour fail before the target is touched. Late arrivals run only
under an explicit per-run `ApplyOptions { order: Order::AllowLate }`
(`Apply::apply_with`, `Inspect::plan_with`), after the installed versions and
with new installation ranks; the report lists them in `late`. Each successful transactional body commits with history and
attempt completion; a failed later body rolls back without undoing earlier
commits. A nontransactional body (`Policy::NonTransactional`, on PostgreSQL and
MySQL) runs in autocommit. Drivers dispatch its statements one by one using
`split_script`. A failure after a statement was dispatched leaves its attempt
unresolved (`Error::Uncertain`) instead of recording a replayable failure; a body
refused before dispatching anything records an ordinary failed attempt. SQLite
uses a durable cooperative claim across commits, PostgreSQL a session advisory
lock and MySQL a named session lock. There is no automatic takeover, and no run
repeats a body. An interrupted transactional attempt is reconciled as rolled
back by the next apply, which then stops with `Error::Reconciled`; a later
apply runs it again. Uncertain nontransactional attempts and stale
SQLite claims need an operator's `Recover::recover` assertion (`Recovery`,
`RecoveryAction`), which is audited and runs no body. `Inspect::status` and
`Inspect::plan` read a target without exclusion, writes or bodies: its
classification, history, running attempts, pending entries and every
`Blocker`, plus the exact steps apply would run. `Catalog::validate(Engine)`
runs apply's catalog checks offline.

`Revert::revert` undoes installations with authored down bodies, newest
installation first: `RevertTarget::To(version)` undoes the installations above
a version and `RevertTarget::Last(n)` the `n` newest. A planned down body comes
from `PlannedMigration::down` (`sql_migration!`'s `down` file), a scripted one
from `Migration::down`, declared by `MigrationInfo::reversal`; a reversible
artifact's checksum covers its down body. Before the first undo, the runner
refuses a selection that is not the newest installations
(`Blocker::Interleaved`), contains an irreversible one
(`Blocker::Irreversible`) or exceeds the installations (`Blocker::Exceeds`).
Each undo is its own journaled `down` attempt that commits on its own; a later
failure keeps earlier undos, and the `RevertReport` lists the remaining stack.
`Inspect::revert_plan` shows the steps without running them.

A snapshot (`MigrationKind::Snapshot`, `sql_migration!`'s `kind: Snapshot`)
covers every incremental at or below its version; the catalog derives that
manifest and checksums it with the snapshot. On a target whose journal never
recorded a completed installation or coverage (`Session::initialized`),
apply runs the newest snapshot at or below
`ApplyOptions::through` and then the tail, unless `Init::FullReplay` asks for
the incrementals; `ApplyReport` lists the snapshot and what it covered.
`Adopt::adopt` records an operator's `Adoption` of an unmanaged target through
a version, executing no body, and refuses fresh and managed targets with
`AdoptionError`. Either way the target holds one `Coverage` claim: covered
incrementals are not installations, an incremental added later at or below
the boundary is `Blocker::Uncovered` whatever the order permission, and no
revert crosses the boundary (`Blocker::Boundary`).

Every engine keeps its state in one reserved journal table, `_rupa_migrations`,
defined per engine in [`sql/`](sql/) (`postgres.sql`, `mysql.sql`,
`sqlite.sql`), the files the runner executes on a fresh target.

Dynamic adapters remain a subsequent implementation slice.

## Feature flags

| feature | adds |
|---|---|
| `sync` | `sync::{Session, Migration, Context, Apply, Inspect, Recover, Revert, Adopt}` |
| `async` | `asynchronous::{Session, Migration, Context, Apply, Inspect, Recover, Revert, Adopt}` (unboxed `Send` futures); with `sync`, `Blocking<S>` sessions |
| `protocol` | the engine session protocols (`protocol::{postgres, mysql, sqlite}`) and their per-mode `Io` traits, for driver crates; not public API |

Neither is default. With exactly one enabled, all eight of its names are
re-exported at the crate root, and `prelude` brings its method traits (`Apply`,
`Inspect`, `Recover`, `Revert`, `Adopt`, `Session`) into scope anonymously; with both, use the mode modules. The facade
gates the crate with `migrations` and forwards its own `sync`/`async`; driver
adapters have their own optional `migrations` feature.
